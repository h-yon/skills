# 日本語文書の執筆と推敲の規範

日本語で文書（業務文書、ADR、README、レポート、記事、解説文）を書くときや推敲するときは、以下の規範に従う。
推敲では、まず内容を点検して**生成残渣**（依頼や会話といった製造過程の痕跡）を除去し、次に表現を文章規範に照らして点検する。
書くときは、最初から両方を満たすように書く。

## 生成残渣の除去

依頼と会話は、文書を作るための材料と経緯であって、それ自体は文書の内容ではない。読者は会話を見ていない。成果物は、その読者が自分に向けて書かれた一つの文書として通読できるものでなければならない。

### 記述の分類

文書に残す前に、各記述を次の三つに分け、分類ごとに扱いを決める。

- **読者に必要な内容**：文書の対象（設計、手順、仕様）について読者が知るべきこと。そのまま残す。
- **書き方への指示**：依頼者が伝えた制約、読者層、トーン、避けたい表現。文面には出さず、語彙、構成、例の選び方に反映する。
- **会話の残渣**：依頼への応答、修正の経緯、追加の理由、依頼者との合意の確認。削る。

判定の目安は、その記述が指す出来事が文書の対象に属するか、文書を作った会話に属するかである。会話の出来事（指摘、修正、再依頼）は読者の知らない出来事なので残渣になる。対象の出来事（設計の変遷、バージョン間の差）は読者が知るべきことでありうるので、内容として残る。

### 残渣として現れやすい言い回し

- **依頼に応えたことを示す言い回し**。悪い例（PR description）：「ご指摘のとおり、リトライ回数を設定値に移しました」。良い例：「リトライ回数は設定ファイルから読む」。
- **以前の版や修正の経緯への言及**。悪い例（README）：「以前の説明は誤っていたため、以下に訂正する」。良い例：訂正後の説明だけを置く。
- **依頼で与えられた制約や禁止を断り書きにしたもの**。悪い例（技術解説記事）：「本記事では、指示により外部ライブラリの比較は扱わない」。良い例：比較の節を置かず、標準機能での実装だけを書く。
- **依頼の前提をそのまま写した前置き**。悪い例（技術解説記事）：「読者は TypeScript に慣れているがジェネリクスには不慣れ、という前提で書く」。良い例：前置きを消し、型注釈の基礎は説明せず、ジェネリクスの説明に紙幅を割く。
- **節や段落が追加された理由の説明**。悪い例（ADR）：「レビューで可観測性が足りないと指摘されたので、以下に節を足す」。良い例：「## 可観測性」の見出しの下に内容だけを書く。
- **チャットの返答の名残**。悪い例（README）：「ご質問ありがとうございます。必要であれば、次にデプロイ手順も追記できます」。良い例：削る。

依頼への応答を疑う手がかりは、読者が思ってもいない書き方を打ち消す語（「一般論ではなく」「抽象的な話ではなく」）と、トーンや書き方の指定（「やさしい言葉で」「断定を避けて」）が本文に残っていることである。

### 読者が必要とする経緯

残渣に見える記述でも、読者がその情報を必要とするなら残す。機械的に消さない。

- ADR の「検討した選択肢と却下した理由」は設計の経緯であり、後からその決定を読み直す人に必要である。残す。
- README の「v2 で設定ファイルの形式が変わった」は、v1 から移行する読者に必要である。残す。
- PR description の「最初は同期呼び出しで書いたが、レビューでキュー経由に変えた」は、変更の理由（なぜキュー経由か）だけを残し、レビューのやり取りは削る。

### 会話中で示された例の扱い

- 依頼者が意図を伝えるために出した例（「〇〇のブログのような調子で」「こういう書き方は避けて」）は、抽象度、読者層、トーンを診断する材料であって、成果物の内容ではない。
- 例が意図せず文書の主題になっていないか確かめる。悪い例（技術解説記事）：「避けたい書き方」として貼られた文がキャッシュ戦略の説明だったため、本文にキャッシュの段落が紛れ込む。
- 例の題材と成果物の主題が重なっているときは、その重なりが依頼の主題から来ているかを確かめる。

### 制約の反映

依頼で指定された制約は、断り書きとして文面に出さず、語彙、構成、手順、例の選び方に反映する。

悪い例（README）：「本 README では、依頼により Kubernetes での運用には触れない。また専門用語を避けるよう求められているため、平易に書く」と前置きしてから手順に入る。
良い例（README）：前置きなしに「ローカルで動かす」の節から始め、Kubernetes の節を置かず、用語は言い換えて書く。

制約の種類ごとの反映先は次のとおり。

- 使わない道具（「Docker は使わない」）：手順からその道具の工程を外し、代わりの手順を書く。「Docker は使いません」と書かない。
- 避ける言葉（「エンジニアではなく開発者」）：語彙を差し替える。言い換えた旨を注記しない。
- 想定読者の水準（「新人向け」）：前提知識の説明量と例の難度を変える。「初心者向けに書いた」と書かない。
- 触れない話題（「料金には触れない」）：構成からその節を外す。読者が確実にその話題を探すなら、参照先の一文だけ置く（これは読者に必要な内容に当たる）。
- トーン（「断定調で」）：文末と修飾語で実現する。「断定調で書いている」と書かない。

## 表記

- コード、差分、ログ、設定ファイルの断片はコードブロックで示す。
- 定義や分類の列挙は箇条書きで示してよい。定義される用語は太字にする。
- 用語を本文中で初めて定義または導入するときも、その語は太字にする。すでに導入した語を話題として指すとき、引用、通称には「」を使い、太字と使い分ける（初出の定義は太字、以後の言及は「」）。
- ダッシュ（em ダッシュ `—`、horizontal bar `―`、いわゆる2倍ダッシュ「——」）を日本語の地の文と見出しで使わない。同格や補足の挿入（「A——挿入——B」）は括弧（）に、言い換えや敷衍（「A——B」）は句点で二文に分けるか読点でつなぐ。範囲を示す en ダッシュ `–` や英語の複合語（`Curry–Howard` など）、コードブロック、書誌情報は対象外。
- 中黒（・）を日本語の並列で使わない。ただし単一の固有名詞の内部では使ってよい。
- 見出しに、区切り線（罫線 `─` U+2500 やダッシュ類）で「種別──主題」「主題──概念」のように二要素を詰め込まない。見出しは単一の自然な句にする（要素を一つに絞るか、助詞や読点でつなぐ）。
- 用語とその定義を並べる箇条書きは、区切り線ではなく全角コロンで「**用語**：説明」と書く。

## 段落と論証の構成

**パラグラフライティング**を基本とする。段落は論証の一歩であり、読者は段落単位で論理を追えなければならない。

- 一つの段落には一つのトピックだけを置く。場面の進行（調査、報告、検証、評価）が複数混ざった長い段落は、一歩ずつの段落に分割する。
- 段落の最初の文を読めば、その段落が何の話かわかるようにする。
- 段落の先頭では、前の段落との論理関係を接続表現で明示する（「であれば」「実際」「しかし」「この例自体からも」）。
- 結論の置き場所は文書の型で決める。どちらの型でも、同じ結論を二度置かない（結論を出してから反論を処理し、結論を言い直す構成にしない）。
  - **論証型**（解説記事、書籍の章）：論証を一方向に進め、反論と疑念の処理を終えてから、結論を一度だけ置く。
  - **報告型**（ADR、PR description、レポート、README）：結論（決定、変更の要点、結果）を文書の冒頭と各節の第一文に置き、根拠と経緯を後に並べる。末尾で結論を言い直さない。先に示すのは本文の第一文であって見出しではなく、見出しは対象を指す名詞句にする（「見出しの付け方」）。
- 例への弁明（作為的に見える、への先回りなど）は、場面の山場の直後に挟んで流れを切らない。次の節の冒頭でまとめて処理する。
- 読者が立てそうな誤った解釈は、明示的に否定してから本当の理由を述べる（「その理由は『〜だから』ではない。〜だからだ」）。
- 「AではなくB」と否定するときは、否定の根拠を一文添える。反実仮想（「もしAなら、〜だっただろう」）が使えることが多い。
- 「AではなくB」の否定部は、読者がAだと誤解する見込みがあるときだけ書く。誤解の見込みがなければ「Aではなく」を省き、Bだけを述べる。
- 同じ概念を二つの対象で対比定義するときは、両文の述部を同じ型にする。既出の説明の回収は文頭の枠に置き、定義そのものを「〜だと説明した」に埋め込まない。特徴の句は「」で切り出し、対比の接続を明示する。第二極について続ける属性は、主語を改めて名乗らず継承する。
- 譲歩（「確かに〜」）では、事実の確認にとどめる。あとで訂正する内容を著者の声で因果として断定すると、自己矛盾になる。表面的な診断を一度認めたいときは、読者や通説の声に帰属させる（「〜と要約できてしまうかもしれない」）。
- 論証型では、山場で効かせたい情報（数値、固有の事実）を、その手前の段落で先出ししない。
- 何かを否定または限定するときは、否定する命題そのものを「」で正確に書き出す（「明文化されていればすべてを任せられる」を意味しない、など）。「何もかもが解決するわけではない」のような漠然とした否定で済ませない。
- 「後述する」のような前方参照は、論証が一段落した位置（段落末や節末）に置く。論証の途中に挟んで流れを切らない。

## 論証の厳密さ

文章の論理にツッコミどころを残さない。書き上げたら、読み手の反論を先回りして次の点を点検する。

- 推量、可能性、読者の疑念、反実仮想として書かれている文を、機械的に断定へ変えない。
  「かもしれない」「だろう」「ようだ」「らしい」は、根拠なく主張を弱めている場合だけ削る。
  事実未確認の可能性、作中人物の認識、ログからの推定、読者が抱きそうな疑念、反実仮想を表す場合は、その不確実性を保つ。
  断定に直せるのは、本文内の根拠によって命題が確定している場合に限る。
  悪い例：「提示し続けているかもしれない」を「提示し続けている」に変える。
  良い例：「提示し続けている可能性がある」のように、不確実性を残して文を整える。
- 異なるものを「同じ」とまとめない。区別すべき対象（別々の決定、別々の原因、種類の違う問題）を一括りの言葉でくくらない。悪い例：相互依存する三つの未決事項を「同じ決定を別々に下していた」と書く。良い例：「どれも別々の決定であり、しかも互いに依存している」と腑分けする。
- 複数の要因がある事象を、単一の原因に還元しない。例が複数種類の問題を含むなら、それぞれを切り分け、どの道具がどれを説明するのかを対応づける。悪い例：契約の不在と情報隠蔽の失敗が混ざった事故を、丸ごと「情報隠蔽の問題」と説明する。
- 文書全体で、同じ概念の扱いを一致させる。ある節で「人間が決める」と分類したものを、別の節で「チームで合意する」と書かない。分類、定義、用語の地位は全体で揃える。
- 因果を主張するときは、その機構（なぜそうなるのか）を一文で示す。「AだとBになる」とだけ書いて理由を省略しない。悪い例：「手順で分けると変更が全体に波及する」。良い例：「各工程がデータを受け渡すための表現を共有してしまい、その表現を変えると全体に波及する」。
- 検出、保証、解決を「必ず」できるかのように書かない。条件付きで正確に述べる（「〜しやすい」「〜できることが多い」「〜が成り立つときに限り」）。
- 二重否定や入れ子になった条件を畳むときは、真偽と条件の対応が元と同じかを確かめる。「通知が無効でない限り送る」と「通知が有効なら送る」は、設定が未指定のときの挙動が違う。
- 主張は、挙げた例が実際にその全体を支えているかを確認する。例が主張の一部しか支えないなら、主張の範囲を例に合わせて狭める。
- 冒頭の要約や見出しで、本文の条件を落とさない。条件の消えた結論は、本文より強い主張になる。悪い例：本文が「月額プランで、連続 12 か月以上利用した契約は解約手数料が無料」と言っているのに、冒頭で「長く使えば解約手数料は無料」と書く。要約に収まらないなら二文に分け、見出しは話題を示す名詞句にする。本文が予定や推定で書いていることを、冒頭や見出しで断定しない。
- 「次節で扱う」と前方に逃がした論点は、本当にそこで回収されることを確認する。回収しない伏線を張らない。
- 譲歩や限定（「ただし」「とはいえ」）を置いたら、その後で必ず論を進める。逆接で終えて宙吊りにしない。
- 節の中心となる語は、その節以前に定義と対象範囲を述べてから使う。定義せず使い始めない。
- 複数の概念を一つの上位語にまとめるときは、命名の直前に、それらが同じものに帰着すると一文で述べる。

## 読み手の負荷の管理

読者の記憶と注意は有限の資源として扱う。

- 読者が順読みで保持する情報は、一度に一段だけ増やす。箇所を削ったら残った言及を辿り、この文書のほかで使われなくなった主題は落とす。直前までの文の上に一段で足りる許可や読み方は直接書く。
- 後で参照する必要のない固有名（ファイル名、関数名、識別子）を出さない。「仕様書」「金額計算のユーティリティ」のような一般的な言い方で済ませる。
- 抽象的な言い回しの指す内容が文脈から一意に決まらないときは、可能なときは丸括弧による同格挿入でその場で特定し、できるだけ読者に前を読み返させない。
- 動作を名詞にまとめると、誰が何をするかが消える。「〜への対応」「〜の実施」「〜を担保」「〜を図る」「〜に資する」「〜を行う」は、動作主と対象のある動詞の文に戻す。悪い例：「移行時のデータ欠損への対応を実施する」。良い例：「移行でデータが欠けた行を、移行後に元の表から補う」。判定は、その名詞句を動詞の文に書き直してみて、誰が何をするかがはっきりするなら名詞化が負荷になっている。漢語を助詞なしで詰めた句（「障害発生時連絡先」）も「障害が起きたときの連絡先」とほどく。「ログイン画面」「文字コード」のように定着した複合語はほどかない。
- 概念を初めて示す文では、読者が順に読んだだけで、まずその概念が何であるか（データ構造、手順、制約などの種類や地位）を読み取れる順序にする。その概念を既に知っている読者にだけ自然な性質、仕組み、制約を、種類の同定より前に置かない。前置すると、未習の読者は文を読み終えた時点で逆戻りしなければ核となる情報を見逃すか、理解が滞る。
- 新しい例や場面を追加して、読者が保持すべき文脈が増えるときは、前の例と何が違うのか、なぜもう一つ必要なのかを前置きして納得感を与える。
- 同一節内に図、表、コードなど複数の提示があるとき、各媒体が担う説明（配置の見え方、数値、手順など）を分けて書く。媒体間で型やデータを揃える必要はなく、別例として並べてよい。指示語（「この2つ」「上記の例」）は、どの媒体のどの例を指すか文脈だけで一意に決まるように置く。一つの媒体で確認した性質を、別の媒体の例にもそのまま当てはめない。二方式を「Aの代わりにB」と対比するときも、やめる側と採る側の語順を置換関係と一致させ、後に書く側が採用される方式であることを順読みで読み取れるようにする。
- 文書の冒頭や節の導入では、これから例で扱う内容に関係しない過剰な詳細を詰め込まない。
- 例の節の中でも、**その節の問いと帰結に関係しない**過剰な詳細だけを省く。議論に必要な具体は残す。省略の典型は、エージェント報告の装飾的精度（時刻、HTTP ステータス、カバレッジ率など）や、後で参照しない固有名詞。
- 例示を、執筆のきっかけになった個別事例の固有情報（固有名、日時、数値）のままにしない。示したい性質が伝わる一般形に置き換える。実在の固有名を残すのは、読者がそのまま使う実用情報（実在の識別子、コマンド、設定名）に限る。
- 文書や知見の出自や経緯（「〜の調査で得た知見を元にしている」「元は〜だった」）は、読者の理解や行動を変えないなら書かない。意外性の提示や信頼度の根拠づけなど、載せる理由が明確なときだけ書く。

## 視点と語り

- 例示では、結果の羅列や受動態（「特定され、判明した」）ではなく、行為者を主語にした動作の連なり（「リポジトリを調査して特定し、見つけてくれた」）で書く。
- 「入社2年目のエンジニアが」のような架空の人物設定を無意味に冠しない。
- 論証の中で読者を「あなた」と呼ばず、役割名（「開発者」「読者」）で書く。二人称の呼びかけは、場面への導入（「〜としよう」）や文書の結びなど、限られた要所にとどめる。
- 対象を指す語は具体的に選ぶ。「AI」「ツール」のような広い語でぼかさない。
- 文書内で定式化や術語を導入したら、以後はその語で通す。「文脈」「ツール」「AI」のような曖昧語に後退しない（定式化する前の導入語として「文脈」などを使うのはよい）。
- 術語や訳語は、その分野で慣用されている語を選ぶ（プッシュ通知は「配送」ではなく「配信」、など）。意味の近い漢語を一般語の感覚で充てない。
- 人物そのものに言及するときは原綴りで書く（Lehman、Bainbridge）。ただし、歴史上の人物や、人名を冠した概念を定着名で紹介するときは、日本語で通用しているカタカナの通称を使う。
- 術語の響きを持つ語を、術語でない場面に流用しない（システムから人間までの連なりを「経路」と呼ぶ、など）。「届くまでの流れ」「あいだに何があるか」のように普通の言い方で書く。

## 演出の抑制

演出の規範は全面禁止ではなく、節度の規範である。修辞は、それが効果を生む箇所でのみ使う。

- 溜め（「ここには〜が潜んでいる」）や修辞疑問で導出を演出するのは、緊張が議論に効く要所に限る。説明で足りる箇所では、そのまま述べる。
- 短い決め台詞を独立した段落にして緊張を作る演出を多用しない。段落内の短い体言止め（「ここまでわずか数十秒。」など）は、場面の山場に限り使ってよい。
- 本文中の太字強調を多用しない。誤読を防ぐ否定や節の帰結など、論理の要所に限り、一節に一、二箇所まで使ってよい（導入部でも可）。それ以外は文の順序と構造で際立たせる。
- 「〜してはならない」という命令調の断定より、「〜するわけにはいかない」のような、作業者の判断として書く形を選ぶ。
- 転回点を過剰に劇的にしない。事実を述べる一文で足りる場合が多い。議論の山場にかぎり、感嘆符つきの短い一文程度は許容する。
- 帰結の列挙によって事故や危険を煽らない。
- 「AではなくBだった」という対句の決め台詞を多用しない。軽い補足や評価は括弧書きで添えてよい。
- 慣用表現をひねった言い回し（「知識を体に入れる」など）や、指す内容が一意に決まらない比喩（「報告の外側に世界が広がっている」など）を使わない。平易な動詞でそのまま言う（「身につく」「気付く機会が減る」）。

## LLM っぽい表現の禁止

LLM が大量生成する、中身のない型に誘惑されない。書き上げたら、この節で点検する。
その文書で定義した術語を議論に使うのはよい。空虚な装飾として使うのが問題である。

次のような言い回しは、論点を増やさず「ちゃんと書いている感」だけを付ける LLM 口調である。使わない。

- **予告と総括**：「重要なのは〜である」「本稿では〜を扱う／探求する」「ここでは〜について見ていく」「本記事では〜をご紹介します」「それでは見ていきましょう」「以下で詳しく説明します」「まとめると」「要するに」（直前の言い換えだけのとき）、「〜に他ならない」。ただし、主張の様式を宣言する前置き（「標語として言い換えれば」など）や、扱う範囲と対象読者を示す導入は使ってよい
- **正面から系**：「正面から扱う」「正面から回収する」「正面から見る／書く／立てる」（中身の代わりに姿勢だけを宣言する）
- **空虚な形容**：「不可欠」「核心的」「鍵となる」「根本的な」（主張の中身を説明せず強調だけする）、「多角的」「包括的」「総合的」（何をどう見たかを書かない）
- **空虚な動詞**：「掘り下げる」「深掘りする」「言語化する」（何をどう書いたかを示さず終わる）、「触れる」「言及する」（一段落で済ませるだけ）
- **接続の型**：「〜において」「〜という側面から」「〜の観点から」（新情報なし）、「さらに」「また」「加えて」の連打
- **弱い緩和と称賛**：「〜と言えるだろう」「〜かもしれない」（根拠なく主張を弱める場合だけ）、「非常に」「極めて」「大いに」（中身のない強調）
- **数の宣言**：「ポイントは 3 つです」「理由は 3 つあります」「大きく 3 種類に分けられる」。項目から直接書き始めるか、続く中身と一文にまとめる。素材にない数の枠を作って構造を装わない
- **定型の結び**：「いかがでしたでしょうか」「ぜひ参考にしてみてください」「お役に立てれば幸いです」「まずは小さく始めましょう」。本文の自然な結びで終える
- **先回りの打ち消し**：誰も言っていない思い込みを先に否定する文（「テストを書けば、それだけで設計がよくなるわけではない」）。言いたい中身は次の文にあるので、文ごと削る。文頭の「もちろん、」に数語だけ続く短文（「もちろん、例外はある。」）も同じ型。読者が実際に誤解しそうな場合の否定は「段落と論証の構成」のとおり残す

悪い例：「本稿では、〇〇の理論を正面から扱う」「この前提を、ここで正面から回収する」「多角的に分析すると、重要なのは〜である」。
良い例：「本稿では、〇〇の理論を扱う」「ここで、この前提を回収する」「評価の核心は、正しさを誰が知っているかにある」。

## 翻訳調の比喩と擬人化の禁止

LLM は、日本語として存在しない言い回しを、次の三つの経路で生成する。
前節の空句と違い、書き手（LLM）に比喩や演出の意識がないまま混入するので、比喩を使ったつもりのない文も含めて点検する。

- **英語慣用句の直訳**：英語の技術文では carry / open / expose / live / land などの比喩的用法が慣用句として定着しており、比喩として意識されない。これを日本語の対応語に直訳すると、日本語では慣用化していないため、字義どおりに読める奇妙な生きた比喩になる。
  - 悪い例：「ベクトルが選好を運ぶ」（carry）。良い例：「選好がベクトルとして表現される」「ベクトルに反映される」。
  - 悪い例：「この問いは開かれている」（open question）。良い例：「この問いにはまだ答えが出ていない」「未解決である」。
  - 悪い例：「推敲の軸が露出する」（expose）。良い例：「推敲の軸が線形に取り出せる」。
  - 悪い例：「この情報は残差ストリームに住んでいる」（live in）。良い例：「残差ストリームに含まれる」。
  - 悪い例：「設定を変えると既存のキャッシュが静かに壊れる」（silently break）。良い例：「設定を変えると、既存のキャッシュが気づかないうちに使えなくなる」。「静かに」「黙って」は、警告が出ないという仕組みを知っているなら「警告を出さずに」と書き、知らないなら「気づかないうちに」の幅で書く。
- **術語の直訳**：英語の技術用語を一語ずつ日本語に置き換えた語は、定着した訳語かカタカナ語に直す。「版」（version）は「バージョン」、「回帰」（regression）は「リグレッション」か「以前は動いていた〜が動かなくなった」、「正本」（single source of truth）は「唯一の参照元」、論理や議論の「接続」（connect）は「関連づける」「つなぐ」、「一級市民として扱う」（first-class citizen）は「ほかと同じ扱いにする」、「優雅な劣化」（graceful degradation）は「機能を段階的に落とす」、「端のケース」（edge case）は「エッジケース」「境界条件」。「改訂版」「回帰テスト」「依存性の注入」のように、その分野で定着した訳語は対象外。
- **無生物主語構文の直輸入**：英語では無生物主語の他動詞文が普通だが、そのまま日本語にすると、モデル、データ、ベクトル、損失といった抽象物が意思を持って振る舞う擬人化になる。日本語では、人か処理を主体に戻すか、「〜から分かる」「〜に含まれる」の形に言い直す。直す対象は、感情や意志を持たせた文に限る。道具や仕組みの働きを客観的に述べる無生物主語（「このジョブは失敗した行を退避用の表に移す」「監視が閾値超えを検知する」）は自然な日本語であり、残す。
  - 悪い例：「モデルは文体を知っている」。良い例：「モデルの出力には文体の一貫性がある」など、確認できる事実として書く。
  - 悪い例：「データが語るのは〜である」。良い例：「データから分かるのは〜である」。
- **話し言葉の混入**：機械学習の口頭議論で流通する動詞（「効く」「刺さる」「筋がいい」など）や、エンジニアの会話で通じる言い回し（「ログを吐く」「ジョブが死ぬ」「別のキューに投げる」「エラーを握りつぶす」「〜側に倒す」「半日溶かした」）は、話し言葉としては通じるが、書き言葉の技術文書では俗語である。効果、見込み、動作の内容を具体的に書く。
  - 悪い例：「規範スキルが効く」。良い例：「規範スキルを与えると生成が選好に近づく」。
  - 悪い例：「この手法は筋がいい」。良い例：「この手法は〜という理由で有望である」。
  - 悪い例：「失敗したジョブは例外を上に逃がし、ログを吐いて死ぬ」。良い例：「失敗したジョブは例外を呼び出し元に伝え、ログを出力して異常終了する」。
  - 悪い例：「互換性を残さない側に倒した」。良い例：「互換性より構造の単純さを優先した」。
  - 定着しているかは、仕様書やリファレンスのような書き言葉で使われているかで決める。会話で通じるだけでは定着と見ない。「キャッシュが効く」のように、技術的な用法として読み方が一つに決まるものは残す。

判定の目安は三段である。
まず、その述語を初めて見る読者が字義どおりの動作（運ぶ、開く、住む）を想像しうるなら、翻訳調の比喩を疑う。
次に、その語句を英語に訳し戻してみる。英語の慣用句や術語を一語ずつ置き換えた形になっていれば、直訳である。
最後に、動作の主体と対象を具体語で言い直せるか試す。
言い直せるなら、その言い直しをそのまま書く。言い直すときは、元の語に含まれていた評価や気分（「地味に」の目立たないが確かにある、「〜てしまった」の悔い）を平易な語で残し、効き目だけをぼんやり述べる言い換え（「良い方向に働く」）にしない。
言い直せないなら、その文は指す内容が特定できていないので、主張として成立していない。削るか、内容を確定させてから書き直す。

## 冗長の排除

無駄な文章をなるべく残さない。

- 同じ主張を言い換えて繰り返さない。一つの主張は一度だけ書く。題材が直前と同じでも、その文が加えている命題が違えば繰り返しではない。列挙の各項が同じ論理的地位であることを示す枠語の反復や、定義の直後に適用条件や限定を足す文も、主張の繰り返しではない。
- 隣接する節が同じことを別の角度で述べているなら、役割が重複している。片方に吸収して一つの節にまとめる。
- 場面を描写した直後に、その内容を要約し直さない。意味づけの一文（「このような作業は、ほぼ完全に任せられる」など）だけを置く。
- 同じ論理的役割を持つ並列の事実は、文を分けて重ねず一文にまとめる。その事実群の論理的地位は文頭の語で示す（「当然、経理部の月次処理も顧客の支払いも〜」）。
- 冗長さは文字数や文数で判定しない。短文化と一文化は、動機、対象、操作、その同一性、因果、条件が順読みで明示されたまま保てる場合に限る。これらを読者の推論に委ねる圧縮はせず、必要な反復と長さを残す。議論の展開を残して要約を添えるときは、合図として「要するに」を使ってよい。
- 一文に書いた目的や理由を後ろへ切り出して、「〜ためである。」「〜からである。」の短文を新しく作らない。悪い例：「夜間バッチは 2 時に動かす。日中の負荷を避けるためである。」良い例：「日中の負荷を避けるため、夜間バッチは 2 時に動かす。」
- 接続や評価のためだけの文（「それ自体はよいことである」など）を置かない。
- 想像上の読者との問答（問いを立てて一語で答える形など）を修辞として使わない。主張はそのまま述べる。読者の反応を演じて応答する形（「〜と感じたかもしれない。そのとおりである」）も同様に避け、譲歩は地の文で簡潔に行う（「もちろん、処置そのものは開発者が決める問題ではない」）。
- 読者が抱きそうな発想を、メタな枠取り（「ここまでの話には自然な続きがある」「〜という発想である」）で紹介しない。その発想自体を直接書く。読者の疑問なら疑問文のまま書いてよい（「その保守も任せればよいのではないだろうか」）。
- 「本稿もそれを否定しない」のような、著者の立場の弁明や断りを書かない。事実の記述（「〜に書かせる場合が多い」）だけを置く。
- 文脈を最短で読み手と共有できる文章にする。導出を一歩ずつ展開しなくても伝わるなら、構造に名前を与えて言い切る。
- 本文でまだ導入していない概念や文書名を、先回りして持ち出さない。
- ためらいのある弱い述語（「有効な対策であり」など）で済ませない。本文内の根拠で確定していることは強く具体的に言い切る（「活用において必須であり」など）。語調を整えるための意図的な緩和（「必須だと言ってもいい」など）は許す。
- 文章のリズムを作るための接続表現（「しかし一方で」など）は、冗長と見なさない。

## 見出しの付け方

見出しは内容を特定できる具体的なものにする。その節が答える問い、または扱う対象を指す句にする。

- 作業の手順だけを述べる見出し（「例に戻す」「〜を読み直す」など）にしない。
- 見出しを、節の結論を言い切る「セリフ」にしない。見出しの時点で読者がオチを知る状態を避ける。これは論証型と報告型のどちらでも同じで、報告型で結論を先に示す場所は本文の第一文である（「段落と論証の構成」）。
- 疑問形か、対象を指す名詞句かは、本文のトーンに合うほうを選ぶ。
- 本文の条件を落とした結論を見出しにしない。条件が込み入った節は、話題を示す名詞句にする（「論証の厳密さ」）。

## 読者への誠実さ

- 例が作為的に見えうる場合、それを隠さない。読者の疑念を先回りして認め、現実に十分あり得ることの根拠を短く添える。
- その根拠は、著者の断定（「十分あり得る状況だ」）ではなく、読者自身の経験に訴える一般的事実や通説に求める（「この症状は珍しくないだろう」「〜という言い方もよく耳にする」）。
- 確認していないことを、確認したかのように滑らかに書かない。

## 推敲時の点検

推敲を頼まれたときは、「生成残渣の除去」の分類と文章規範の各節の点検項目に加えて、文書全体が一つの声で書かれているかを確かめる。複数回の修正指示を経た文書には、修正ごとの継ぎ接ぎが残りやすい。

- 同じ主張が二箇所にないか。段落を追加したとき、古い段落を消し忘れていることが多い。
- 用語が途中で変わっていないか。最初の版の「利用者」が後の版で「ユーザー」になっている、など。
- 文体が節ごとに違わないか。である調とですます調の混在、箇条書きと地の文の比率の急な変化。
- 後から足した節が、参照する概念の定義より前に置かれていないか。修正の順序で並んだままになりやすい。
- 削った箇所を指す「前述の」「上で述べた」が残っていないか。
- 見出しや注記が読者に向いているか。「追記」「修正版」「レビュー対応」のような見出し、「※ 上記は仮」のような作り手向けの注記、「TODO」を残さない。
- 断り書きや注意書きは、読者が本当に必要とするものだけか。「環境によって異なる場合がある」のような免責は、その違いが読者の行動を変える場合だけ、何がどう違うかを具体的に書く。

## 出力の作法

推敲を頼まれたときは、修正後の文書そのものを出す。

- 何をしたかの前置きを付けない。悪い例：「以下が修正版です。冗長な表現を削り、見出しを整えました」から始める。良い例：文書の一行目から始める。
- 変更の要約も求められたときは、文書を先に、要約を後に置く。
- 何をどう直したかの報告は、求められたときだけ行う。
